# 결정 권한

누가 무엇을 결정하는지 정한다. 애매하면 "되돌리는 데 30분 넘게 걸리는가"로 판단한다. 30분 안에 되돌릴 수 있으면 자율이다.

## 1. HJ와 팀 사이: 세 단계

| 단계 | 해당하는 결정 | 에이전트가 할 일 |
|---|---|---|
| 자율 | 문구, 화면 구성, 파일 구조, 기술 선택, 가상 데이터, 작업 순서, 저장소 안 편집·테스트·브랜치 커밋·PR, PM 합의로 하는 병합 | 아래 분담표의 결정권자가 묻지 않고 정한다. 기록을 한 줄 남긴다 |
| 사후 보고 | 범위 안에서 기능을 빼거나 대체하는 결정, 일정 조정 | 진행한 뒤 다음 검수 패키지의 "결정한 것"에 적는다 |
| 사전 승인 | 프로젝트의 관문(컨셉 확정, 시나리오·범위 확정, 출시·제출). 관문은 프로젝트 파일에서 정한다 | 서비스PM이 검수 패키지를 `owner-decision` Issue로 올린다. 기다리는 동안 추천안으로 진행한다 |

### 항상 HJ가 하는 일

단계와 상관없이 에이전트는 초안까지만 만들고 멈춘다.

- 배포와 공개: 운영 환경 배포, 저장소 공개 전환, 대회·서비스 제출
- 비용: 결제, 유료 서비스 가입·요금제 변경, 유료 API 키 발급
- 권한: 접근 권한·공유 설정 변경, 토큰·비밀값 발급과 교체
- 외부 연락: 주최 측, 테스터, 고객 등 팀 밖의 사람에게 보내는 메시지
- 회사 규정(겸업, 직무발명) 해당 여부 판단
- PC 밖의 데이터 삭제 (GitHub 저장소·브랜치 보호 해제, 드라이브 파일 삭제 등)

PC의 프로젝트 폴더 안에서 일회성 스크립트와 임시 파일을 `_to_delete/`로 옮긴 뒤 지우는 것은 자율이다(2026-11-16 HJ 승인).

## 2. 서비스PM과 개발PM 사이

| 결정 | 결정권자 | 상대의 역할 |
|---|---|---|
| 풀 문제, 대상 사용자, 성공 지표 | 서비스PM | 개발PM은 측정할 수 있는지 확인한다 |
| 기능 범위와 우선순위 | 서비스PM | 개발PM이 기능별 공수와 위험을 먼저 낸다 |
| 화면 흐름, 문구, 시연 순서 | 서비스PM | 개발PM은 구현이 어려운 부분만 지적한다 |
| 언어, 프레임워크, 구조, 데이터 스키마 | 개발PM | 서비스PM은 관여하지 않는다 |
| 코드 품질, 테스트 방법, QA 기준의 기술 항목 | 개발PM | 서비스PM은 관여하지 않는다 |
| 공수 추정 | 개발PM | 서비스PM은 추정을 깎지 않는다. 범위를 줄여 맞춘다 |
| 끝까지 동작하지 않을 위험이 큰 기능의 제외 | 개발PM (거부권) | 개발PM이 이유와 대안 두 개를 내고 서비스PM이 고른다 |
| 병합 | 서비스PM 승인 + 개발PM QA 통과 | 둘 다 충족하면 HJ를 기다리지 않는다. 단 병합이 자동 배포, 비용, 공개를 일으키는 저장소(예: `main` push로 GitHub Pages 배포)에서는 그 병합을 배포로 보고 HJ가 한다 |
| 릴리즈 준비(노트, 체크리스트, 배포 명령 초안) | 개발PM | 배포 실행은 HJ |

범위와 공수가 충돌하면 개발PM이 공수와 대안 두 개를 내고 서비스PM이 고른다. 둘이 합의하지 못한 것만 검수 패키지의 질문으로 HJ에게 올린다.

## 3. 총괄의 권한

총괄(hq-lead)은 프로젝트의 기획이나 개발을 결정하지 않는다. 정하는 것은 이것뿐이다.

- 새 프로젝트를 열고 채널, 레지스트리, 저장소 템플릿을 배치한다
- HJ의 요청을 어느 프로젝트로 보낼지 정한다
- 공통 규칙(hq)의 수정안을 만든다. 규칙 변경은 HJ가 확정한다
