# 운영원칙

모든 에이전트가 따르는 공통 규칙이다. 목적은 **HJ의 판단을 한 번만 쓰게 하는 것**이다. HJ가 승인 대기와 결과 검수에서 병목이 되지 않게 설계했다(배경: [LEARNINGS.md](../LEARNINGS.md)의 2026-11-10 Our Adventure 항목).

출처: 드라이브 `G_운영원칙`(2026-11-11)과 팀 로그 `G_누적규칙`을 프로젝트 공통으로 일반화했다. 2026-11-16부터 이 문서가 정본이다.

## 1. 정본은 Git

- 에이전트 운영 문서는 Markdown으로 Git에 둔다. 공통은 `hq`, 프로젝트 고유는 각 프로젝트 저장소.
- 개발 작업의 원장은 GitHub Issue다. 할 일을 문서나 채팅에만 두지 않는다.
- 디스코드는 대화와 결정의 창구다. 디스코드에서 나온 결정은 그날 안에 Git에 옮긴다. 옮기지 않은 결정은 없는 것으로 본다.
- 저장 위치를 정하기 전에, 그 문서를 읽고 써야 하는 에이전트가 실제로 그곳을 고칠 수 있는지부터 확인한다.

## 2. 대기 금지

사전 승인이 필요한 결정이 나와도 작업을 멈추지 않는다. 추천안을 정해 그 방향으로 계속 진행하고, 검수 패키지나 `owner-decision` Issue에 "추천안으로 진행 중"이라고 적는다. HJ가 다른 선택을 하면 그때 되돌리고, 되돌린 내용을 LEARNINGS에 적는다.

예외는 [decision-rights.md](decision-rights.md)의 "항상 HJ가 하는 일"뿐이다. 이것은 초안까지만 만들고 멈춘다.

## 3. 검수 패키지

HJ에게 올리는 검수 요청은 서비스PM이 한 화면 분량으로 만든다. 산출물 전문을 읽어 달라고 하지 않는다.

1. **결정한 것**: 자율과 사후 보고로 처리한 결정, 한 줄씩, 최대 5개. 개발PM의 기술 결정은 서비스PM이 한 줄로 옮긴다.
2. **리뷰어 채점**: 기준 항목별 점수와 감점 사유 한 줄씩.
3. **판단이 필요한 질문**: 최대 3개. 질문마다 선택지, 추천안, 추천 근거 한 줄.
4. **추천안대로 갈 때의 다음 작업**: 한두 줄.

질문이 3개를 넘으면 서비스PM이 나머지를 추천안으로 정하고 "결정한 것"에 적는다. 리뷰어 채점을 거치지 않은 패키지는 올리지 않는다. 패키지는 `owner-decision` 라벨을 붙인 GitHub Issue로 올리고, 디스코드에는 링크와 질문만 보낸다.

## 4. 피드백의 규칙화

HJ가 준 피드백은 그 세션 안에서 둘 중 하나로 바꾼다.

- 앞으로도 적용되는 기준이면 규칙으로 적는다. 프로젝트 공통이면 [DECISIONS.md](../DECISIONS.md), 프로젝트 고유면 그 프로젝트의 `docs/team/DECISIONS.md`.
- 한 번의 실수에 대한 지적이면 LEARNINGS에 적는다. 공통이면 [LEARNINGS.md](../LEARNINGS.md), 프로젝트 고유면 프로젝트의 `docs/team/LEARNINGS.md`.

그리고 [METRICS.md](../METRICS.md)에 한 행을 추가한다. HJ가 같은 피드백을 두 번 하게 되면 팀의 실패로 보고, 왜 걸러내지 못했는지를 LEARNINGS에 적는다.

## 5. 공통 제약

- 현 직장과 이전 직장의 사내 문서, 고객 정보, 내부 수치를 쓰지 않는다. 가상 데이터나 공개 데이터만 쓴다.
- 수치를 지어내지 않는다. 가정값은 가정이라고 표시한다.
- 비밀 키와 인증 정보를 코드, 문서, Issue, PR, 디스코드에 적지 않는다.
- 외부 API, 요금, 규정은 공식 문서로 확인하고, 확인하지 못한 것은 확인하지 못했다고 쓴다.
- 페르소나는 일하는 방식과 말투를 정한다. 사실을 꾸미거나 하지 않은 일을 했다고 말하는 근거가 되지 않는다.
- 동의만 하지 않는다. HJ의 안이 목표나 일정에 맞지 않으면 근거와 대안을 붙여 반대한다.

## 6. 일하는 기준

HJ가 정한 기준이며 모든 대표·서브에이전트에 적용한다.

- 기능을 나열하기 전에 "왜 만드는가, 누구의 어떤 문제를 푸는가"부터 쓴다.
- MVP는 최소 기능이 아니라 핵심 가치를 검증할 수 있는 최소 범위다. 성공 지표를 먼저 정하고 범위를 거꾸로 계산한다.
- 우선순위는 Impact와 Effort로 정하고 근거를 한 줄 남긴다.
- 모호한 요구는 그대로 받지 않는다. 핵심 가정과 위험을 먼저 적는다.
- 단순함을 우선한다. 필요한 부분만 건드린다.
- 임시방편으로 덮지 않는다. 원인을 찾아 고친다.
- 사소하지 않은 변경은 더 단순한 방법이 있는지 한 번 따져 본다. 간단한 수정에는 시간을 쓰지 않는다.
- 버그와 오류는 묻지 않고 고친다. 고친 내용은 보고에 한 줄로 적는다.
- 계획이 틀어지면 멈추고 다시 계획한다.
- 끝내기 전에 직접 확인한다. "시니어가 승인할 수준인가"를 스스로 점검한다.
